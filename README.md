# CaptureInterp

把采集卡送进 Mac 的游戏画面从 30 帧补到 60 帧，全屏显示，并播放采集卡的声音。

Frame interpolation (30 → 60 fps) for a game console captured through a UVC capture card on Apple Silicon Macs. Chinese documentation below; the code comments are in English.

主机（比如 PS5）接采集卡，采集卡接 Mac，程序读采集卡的画面，在每两张画面之间算出一张中间画面，按屏幕刷新时刻交替送上屏。不抓屏，不串流。

这是一个自用的小工具，在一台机器、一块采集卡、一块显示器上调出来的。别的设备上能不能直接用好，没有验证过，见文末「已知限制」。

## 需要什么

- Apple Silicon 的 Mac，macOS 26 或更新
- 一块 UVC 采集卡（免驱、系统里能当摄像头认出来的那种），能输出不压缩的 NV12
- Xcode 命令行工具和 Metal 工具链（`xcodebuild -downloadComponent MetalToolchain`）
- 主机端关掉 HDCP、HDR、VRR、120Hz

## 编译和运行

```sh
./build.sh
open -n CaptureInterp.app --args --rife fast --fps 60 --audio auto
```

源码路径里不要有中文或空格。第一次运行系统会问摄像头和麦克风权限，采集卡在系统眼里就是摄像头和麦克风。

没有指定屏幕时，程序自动选外接屏里尺寸最大的那块；没有外接屏才用内屏。

看有哪些设备和档位：

```sh
CaptureInterp.app/Contents/MacOS/CaptureInterp --list
```

## 运行中的按键

| 键 | 模式 |
|---|---|
| 1 | 直通，不补帧 |
| 2 | 补帧，系统引擎单块（补出的帧是 720p 放大，偏软，延迟最低） |
| 3 | 补帧，系统引擎分块（启动时用 `--tiles 4` 或 `--grid` 指定怎么分） |
| 4 | 补帧，显卡整张，运动估算用 1/4 尺寸（延迟低） |
| 5 | 补帧，显卡整张，运动估算用 1/2 尺寸（画质好，4K 下贴着算力上限） |
| H | 状态条常显 |
| Q / Esc | 退出 |

2、3 用的是 macOS 自带的 `VTLowLatencyFrameInterpolation`，一次只收 1280×720，所以要分块再拼。4、5 用的是 RIFE 4.25 的 Metal 实现（见 `THIRD_PARTY_NOTICES.md`），整张一次算完。

## 常用启动参数

| 参数 | 作用 |
|---|---|
| `--fps 60` | 按 60 帧采集，由程序从中挑出游戏的 30 张新画面。不带就是 30 帧采集 |
| `--max-width 2560` | 只用不超过这个宽度的采集档位（比如强制 2K） |
| `--rife fast` / `--rife balanced` | 启动就进 4 档 / 5 档 |
| `--tiles 4` | 启动进 3 档，2×2 分块，约 2K |
| `--grid 3 3 1280 720 16 8` | 3 档自定义分块：列、行、块宽、块高、横向重叠、纵向重叠（重叠须是 4 的倍数） |
| `--orig-native` | 3 档里原画按采集尺寸显示，只有补出的帧是分块尺寸 |
| `--no-interp` | 启动进直通 |
| `--audio auto` | 播放采集卡的声音，延时跟画面对齐。`--audio-gain <dB>` 调音量，默认 20 |
| `--screen-name <名字>` / `--screen <序号>` | 指定输出屏幕 |
| `--device <名字>` | 指定采集设备 |
| `--log <路径>` | 日志位置，默认 `~/Library/Logs/CaptureInterp/stats.log`，每秒一行 |

排查用的开关：`--lead-ms`、`--margin`、`--stepping`、`--no-protect`、`--protect-cpu`、`--single-mid`、`--vote-pick`、`--legacy-pick`、`--steady-offset`、`--gpu-phase-ms`、`--dump <目录>`。含义见 `main.swift` 开头的 `Options`。

## 测试用的设备和设置

所有数字和参数都是在下面这一套上得到的。

**采集卡：阿卡西斯（ACASIS）VC-009Pro**

- USB 3.0 设备，连接速度 5 Gb/s，免驱（UVC），主控芯片厂商显示为 ITE。换更好的线或接雷电口不会更快。
- 有 HDMI 输入和 HDMI 环出两个口。环出口出来的是主机原画，不经过电脑。
- 系统里报出的不压缩档位：

| 分辨率 | 像素格式 | 最高帧率 | 实际表现 |
|---|---|---|---|
| 3840×2160 | NV12 (420v) | 30 | 不能用：每秒只送 27–29 张，间隔不匀，送达延迟 40–60 毫秒 |
| 3840×2160 | NV12 (420v) | 60 | 正常，本程序 4K 档用的就是它 |
| 2560×1440 | NV12 (420v) | 60 / 144 | 正常 |
| 2560×1440 | YUY2 (yuvs) | 50 | 没用过 |
| 1920×1080 | NV12 (420v) | 120 / 240 | 没细测 |
| 1280×720、640×480 | NV12 / YUY2 | 60 | 没用过 |

- 它只有整 60 / 30 帧档（系统里显示为 60.0002 和 30.0000），没有 59.94。主机输出是 59.94Hz，所以每 16.7 秒差出一张画面，送达延迟在 8–25 毫秒之间呈锯齿状来回走。这一条决定了等待压不到更低。
- 会话启动后它会把帧率重置成 25 帧档，程序在启动后会再锁一次帧率。
- HDMI 送来的声音电平很低，程序默认放大 20 分贝。声音是 48kHz 立体声；主机若按多声道输出，环绕和中置声道会丢，主机端要设成 2 声道线性 PCM。

**主机：PS5**

- 视频输出 4K、60Hz（实际 59.94），HDR 关，VRR 关，120Hz 输出关，HDCP 关。
- 不要把输出强制成 1440p：试过，没有好处。
- 测试的游戏是 30 帧模式的开放世界游戏。重场景下它自己会掉到 27–29 帧。

**电脑和屏幕**

- MacBook Pro，M5 Max，macOS 26。
- Studio Display，5K（5120×2880）60Hz，接在电脑上。4K 画面在这块屏上要放大 1.33 倍，2K 画面正好放大 2 倍。
- 没有在电视上试过。

## 实测数字

「等待」指从采集时间戳到这张原画的计划上屏时刻，不含采集卡内部延迟和显示器自身延迟。

| 采集 | 模式 | 每张补帧耗时 | 等待 |
|---|---|---|---|
| 4K 60 | 4 档 显卡·延迟低 | 约 17 毫秒 | 67–85 毫秒 |
| 4K 60 | 5 档 显卡·画质好 | 约 29 毫秒 | 约 83 毫秒 |
| 4K 60 | 3 档 九格拼 4K（`--grid 3 3 1280 720 16 8 --orig-native`） | 约 30 毫秒 | 77–94 毫秒 |
| 2K 60 | 3 档 四块约 2K（`--tiles 4 --max-width 2560`） | 约 18 毫秒 | 约 64 毫秒 |
| 任意 | 1 档 直通 | — | 十几毫秒 |

同一档每次启动会差出一格刷新（约 17 毫秒），取决于启动时和屏幕刷新对上的位置。

等待里各部分大致是：采集卡送达 8–25 毫秒，补帧 17–30 毫秒，安全富余 13 毫秒，对齐屏幕刷新 0–17 毫秒，原画排在补出那张后面一格 17 毫秒。

## 调这个程序时踩到的几件事

写在这里，是因为它们都属于「日志数字全对，眼睛看着却在闪」，换一套设备很可能还会遇到。

1. **交画面的时刻。** 4K 或 BGRA 的大画面，交给显示层的时刻离屏幕刷新太近会赶不上那一格，两张画面挤进同一格，下一格空着。看起来是闪，严重时等于没补帧。程序日志只知道计划时刻，看不出来。
2. **主机 59.94Hz 对采集卡 60Hz。** 采集卡没有 59.94 这一档时，每 16.7 秒差出一张画面，送达延迟呈锯齿状来回走。
3. **从 60 张里挑 30 张。** 60 帧采集下，重复的那张和前一张逐位相同。按「完全相同」认重复是可靠的；按「差别够不够小」来猜，慢镜头和暗场会猜错，30 帧的节奏就会时不时错开一格。
4. **游戏不稳 30 帧。** 重场景里某张画面会停三四格。只补一张会空一格，所以显卡延迟低档在这种间隔里补两张。
5. **字幕和界面。** 它们不动，但运动估算会把它们跟着背景一起扭，隔一张歪一次。程序把前后两张里没变的像素直接取自原画。
6. **别的程序占显卡。** 本机同时跑大模型之类的东西时，显卡档每张会从十几毫秒变成一百多毫秒。

`tools/scprobe.swift` 是量「屏幕上每一格到底有没有换画面」的小工具（ScreenCaptureKit，需要屏幕录制权限）：

```sh
swiftc -O tools/scprobe.swift -o scprobe
./scprobe "Studio Display" 10
```

输出里「two refreshes」的次数就是丢掉的画面数。画面完全静止时它会误报，要在画面持续运动时量。

## 已知限制

- 时间参数（提前 5 毫秒交画面、8 毫秒富余）是在一块显示器上量出来的，换显示器或电视可能要用 `--lead-ms`、`--margin` 重调。
- 只按 30 帧游戏补到 60 帧设计。游戏本身 60 帧时用直通。
- 被遮住又露出来的地方（转视角时的物体边缘）会有虚影，这是靠两张图估算运动的通病。
- 游戏自己掉帧的那几秒仍然会顿。
- 首次进显卡档要编译模型，会卡一两秒。
- 采集卡各档位的好坏差别很大（见上面的表）。换一块卡，先用 `--list` 看档位，再逐个试。
- 没有界面，全靠启动参数和按键。
